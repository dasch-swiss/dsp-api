    ADR-0013: Every endpoint declares its authorization policy; project-scoped policies are enforced by a grant

    Date: 2026-10-31

    Relates to: DEV-7712, DEV-7713, DEV-7714, DEV-7721, DEV-7722, DEV-7723 (the fixed bugs), DEV-7718, DEV-7724, DEV-7725 (follow-ups), slice/common/api/Policy.scala (the policy), slice/common/api/BaseEndpoints.scala (endpoint bases), slice/common/api/AuthorizationRestService.scala (the role rules), slice/common/api/ProjectAdminGrant.scala (candidate and grant), ADR-0011 (context boundaries), the Identity & Access context (docs/contexts/identity-access/CONTEXT.md). Refines the "Authorization is deliberately distributed" decision of the dsp-api domain modularization reasoning (dasch-specs, 2026-07-30).

    Status

    Proposed

    Context

    dsp-api endpoints authenticate, but nothing makes them authorize. The bases in BaseEndpoints (publicEndpoint, securedEndpoint, withUserEndpoint) hand a User to the server logic, and whether that user may do what the request asks is left to each handler. The one exception is bearerSystemAdminEndpoint, which decides in the tapir security logic. Everywhere else authorization is a hand-called check: an AuthorizationRestService.ensure* call in a RestService, or one of about a dozen responder-level mechanisms (ListsResponder.ensureUserIsAdminOrProjectOwner, OntologyCacheHelpers.checkPermissionsForOntologyUpdate, RestCardinalityService, ResourceUtilV2.check*Permission and inline checks). Some of them re-implement the project-admin rule; the ontology one omits the active-user check (not reachable over HTTP, because authentication rejects inactive users, but a copy that drifted). The v3 API wraps the same service in its own V3Authorizer.

    A hand-called check can be missing, swallowed or given the wrong identity, and nothing notices. Eight bugs of this class were fixed together in 2026-10, six of them ticketed:

    • Missing. Deleting list-node comments (DEV-7713) and creating a standoff mapping (DEV-7714) only required a logged-in user. The endpoint descriptions said "Requires authentication.", so the prose described the bug. In DEV-7713 the user parameter was marked @unused, which silences the -Wunused:all -Werror error that would otherwise have flagged it. The ingest asset-overview report dropped its principal (serverLogic(_ => _ => ...)).
    • Swallowed. The anonymous check on resource creation ended in .ignore.
    • Wrong identity. Resource history (DEV-7712) and value deletion (DEV-7723) read the resource as SystemUser, which passes every role and object check, so callers learned facts about resources they cannot see. Two custom-permission checks passed the user IRI where the project IRI was expected (DEV-7721) or did not exempt system administrators (DEV-7722).

    SystemUser passes role checks in four independent places, so reading "as SystemUser" silently bypasses object permissions. Ten main-source files use it outside comments. No test checks authorization across endpoints: the e2e suite enumerates every server endpoint but asserts only that it has an HTTP method.

    The domain modularization reasoning decided that authorization is deliberately distributed: a pure permission-policy primitive, permission administration and effective profiles in Identity & Access, and enforcement by the domain that owns the protected object. The Identity & Access context records the last part: fine-grained object-access enforcement stays with the context that owns the protected object. That decision says where object permissions are enforced. It says nothing about who checks that an endpoint's caller may act at all, and that gap is where the bugs above sit.

    Decision

    The vocabulary is that of XACML and NIST ABAC, mapped onto the monolith in-process. A Policy here is an endpoint's function-level requirement. It is neither the shared Permission policy (permission levels) nor a JWT Scope, and a grant is a proof of one authorization decision, not an Administrative permission.

    1. Every endpoint declares a function-level policy. The endpoint carries a Policy value as a tapir attribute, set by the endpoint factory that builds it, the way NegotiatesOwnAccept.key is set today. The attribute is the machine-readable statement of what the endpoint requires, and tests read it from the completed server endpoint. Policy.requirement renders the sentence the endpoint description must contain, so the prose cannot drift from the attribute again.

    2. The decision point (PDP) is AuthorizationRestService. It is the single home of the role rules. Nothing new re-implements them; the responder-level copies are removed as their slices migrate.

    3. The enforcement point (PEP) depends on what the policy needs.

      • Policies that depend only on the user (Authenticated, SystemAdmin) are enforced by the endpoint factory in the tapir security logic, before the body is decoded. This generalises bearerSystemAdminEndpoint.
      • Project-scoped policies need the decoded input to find the project, so the security logic cannot decide them. They are enforced in the RestService by the candidate-to-grant flow (decision 5).
      • Object-level permissions (view, modify, delete, change rights on resources and values) stay where the owning domain loads the object. The ObjectAccess policy declares this; it does not move the check.

    4. The Policy ADT. The cases and their semantics:

      Case Who passes
      Public(reason) Everyone, without credentials. The reason is reviewed: every public route is an exposure decision.
      Authenticated(reason) Any active, non-anonymous user. The reason is reviewed: "logged in" alone was the DEV-7713 and DEV-7714 bug class.
      SystemAdmin Active system administrators.
      ProjectAdmin(projectFrom) Active system administrators, and active project administrators of the project named by projectFrom (for example "path projectIri", "list node").
      SelfOrSystemAdmin(userFrom) Active system administrators, and the active user named by userFrom (for example "path userIri").
      ProjectAdminOfAnyProject Active system administrators, and active project administrators of at least one project. The check against a specific project stays in the handler.
      ProjectMember(projectFrom) Active system administrators, project administrators and members of the project named by projectFrom.
      ObjectAccess(enforcedIn, admitsAnonymous) Decided per object where the owning domain loads it, and enforcedIn names that place. Anonymous callers are included when admitsAnonymous is true; a write sets it false, and the factory refuses anonymous callers in the security logic.

      ProjectAdmin and ProjectMember keep the semantics of isSystemOrProjectAdmin and isProjectMember: a system administrator is included in both. The active-user check applies to every policy except Public: an authenticated caller must be active, and ObjectAccess with admitsAnonymous also admits anonymous callers. The built-in SystemUser passes every role case too; decision 7 covers it. ProjectMember gets its endpoint factory and candidate type with the first endpoint that migrates to it.

    5. Project-scoped policies use a candidate and a grant. The endpoint factory for ProjectAdmin authenticates and refuses anonymous and inactive users in the security logic, but does not hand the handler a User. It hands over a ProjectCandidate, which exposes nothing a handler can act on. The only way to turn it into something usable is to ask the PDP: authorizeProjectAdminById(candidate, projectIri) loads the project and returns a ProjectAdminGrant, and the domain write methods accept only that grant. Both types have constructors restricted to the slice.common.api package and its subpackages. ProjectCandidate is a plain class so that no unapply leaks the user; the grant's fields stay readable, because responders act on grant.user and grant.project after authorization. Sketch of a migrated RestService method:

      def deleteListNodeComments(candidate: ProjectCandidate)(iri: ListIri): Task[ListNodeCommentsDeleteResponseADM] =
  for {
    projectIri <- listsResponder.getProjectIriFromNode(iri)
    grant      <- auth.authorizeProjectAdminById(candidate, projectIri)
    result     <- listsResponder.deleteListNodeCommentsADM(iri, grant)
  } yield result

    6. The target comes from the grant. A domain write takes its target from grant.project wherever the target is the project itself. Where the target is an object inside the project (a list node), the responder asserts that the object belongs to grant.project and fails with 403 otherwise.

    7. SystemUser elevation is allow-listed, and new uses need review. SystemUser passes every role check, including isSystemAdminOrUser and therefore authorizeProjectAdminById. It cannot arrive over HTTP, because authentication rejects every built-in user, so the risk is in-process code that reads or writes as SystemUser. The legitimate pattern is prefetch-then-check: load as SystemUser, then check the caller's permission on what was loaded before anything reaches the response. The ten main-source files that use SystemUser outside comments are allow-listed, each with a reason. The lint stops new files, not existing uses or new uses inside a listed file; a file added to the list is a reviewed decision.

    8. Undeclared endpoints are tracked by a ratchet, and the bug shapes by a lint. Neither enforces anything at runtime: an endpoint built without a policy-declaring factory is still served, and a declared policy is a label the tests compare, not a measurement of what the handler checks.

      • A test fails when an endpoint has no Policy attribute and is not in a checked-in baseline of endpoints without one, and when the baseline names an endpoint that has since gained a policy or no longer exists. The baseline only shrinks; new endpoints use a policy-declaring factory and never extend it. The test pins the baseline's size, so an appended line fails too; a commit that removes lines lowers the pinned size.
      • The same test fails when a Public or Authenticated policy has a blank reason, or when an endpoint's description does not contain its policy.requirement.
      • just check fails on @unused on a User parameter and on a SystemUser use outside comments in a main-source file, each outside its allow-list (//tools/lint:check_authz, allow-lists in tools/lint/), and on Policy.key or withInfo outside slice.common.api and slice.api.v3.V3BaseEndpoint.
      • An authorization matrix test sends a valid request per migrated endpoint and principal and compares the outcome with a hand-written table, which also must agree with the declared policies.
      • Each responder that checks an object against grant.project is tested with a grant for one project on an object of another.

    9. Migration is complete, except the counts. Every endpoint declares a policy, except the five gravsearch and search count endpoints, which stay in the baseline until DEV-7718 filters counts by the caller's permissions and migrates them to ObjectAccess (DEV-7725). The ensure* helpers of AuthorizationRestService that only the decision point used are private.

    10. This refines, and does not reverse, the decision that authorization is deliberately distributed. Object-level enforcement stays in the owning domain, and administration and profiles stay in Identity & Access. What is added is the layer that decision left open: a declared, tested function-level policy per endpoint, decided in one place.

    Consequences

    What the types guarantee. A domain write that takes a ProjectAdminGrant cannot be reached without one, and the handler of a migrated endpoint holds a ProjectCandidate, not a User, so forgetting the project check before such a write does not compile. A compile-negative test pins that code outside slice.common.api can neither construct a candidate or grant nor read the candidate's user.

    What they do not guarantee.

    • Checking the wrong project still compiles: the grant can be obtained for a project named in the body while the write targets a node in another project. Decision 6 and its responder tests cover this, not the types.
    • A handler that ignores its candidate and calls no grant-taking write compiles. A ProjectAdmin endpoint whose write is not migrated yet is only as safe as its hand-called check.
    • Package access stops accident, not intent. Any file that declares the slice.common.api package can construct a candidate. That is how the test-source helper TestCandidates.of(user) gives tests a candidate; it exists as two identical copies, one in the webapi and one in the test-it test sources. Main sources add no such escape hatch, and review watches for one.
    • Unmigrated endpoints are only as safe as their hand-called checks. The ratchet makes them visible; it does not check them.
    • The remaining bypass routes into the domain are SystemUser (lint allow-list and review) and ObjectAccess (the owning domain).
    • The policy attribute can be overwritten: a later .attribute(Policy.key, ...) in a slice relabels the endpoint, and tapir's withInfo replaces all attributes. The matrix test catches a mislabelled migrated endpoint; elsewhere the rule lives in REVIEW.md.
    • The lint is line-based and only knows @unused on a User. It misses a multi-line annotation, a _ in place of the user and an ignored candidate; the compiler still flags an unannotated unused user.

    Costs. Every endpoint chooses a factory; project-scoped writes change their signatures from User to a grant, and their tests obtain grants through AuthorizationRestService as production does. The ratchet runs in the e2e suite, because enumerating server endpoints needs the full layer, so it fails in CI rather than in just test-unit. Moving a check into the security logic changes the order of answers: a caller without the role gets 401 or 403 before body validation errors. Existence answers that precede the role check (a missing list node answers 400 before 403) stay where the object is publicly readable anyway. Creating a standoff mapping is the accepted exception to authorizing before parsing: its project comes from the body, so the handler parses the body before it obtains the grant, and a malformed body answers 400 to any authenticated caller.

    Enforcement. The endpoint baseline (ratchet: EndpointPolicyE2ESpec over modules/test-e2e/src/test/resources/endpoints-without-policy.txt), the lint in just check (static-analysis), the matrix and responder tests (test), and the REVIEW.md items for Public and Authenticated reasons, policy relabelling and new SystemUser allow-list entries (review).

    Alternatives rejected

    • An external policy engine (Cedar via cedar-java, OPA, Oso, OpenFGA or SpiceDB). None of them stops a forgotten call, which is the bug class here. The rule set is small: three roles and four object permissions. Object permissions live in RDF, so an engine would need a sync layer that is itself an authorization risk, and Cedar would add a native library to the multi-arch images. Revisit only if policies must become data that non-developers edit.
    • Enforce every policy in the security logic. Impossible for project-scoped policies: the project often comes from the body (DEV-7714) or from a list node, and the body is decoded after the security logic.
    • Proof types on every service method now. The strongest guarantee, but it touches about 120 signatures at once. Two pilot slices prove the shape first; the rest migrate incrementally under the ratchet.
